# Weathernews 外部API分析・公開仕様との照合

2026-10-25。対象は利用者指定の https://wxtech.weathernews.com/products/data/api/ 。

## 目的と方法

花粉オープンデータ、天気予報、実況天気の3種類を代表として扱う。外部HTTP応答だけで作れる仕様と、公開仕様でしか分からない情報を分ける。公開例でリクエストを設計しているので、未知APIの完全なブラックボックス発見能力は測らない。

Unbrowseの既存SDK・認証・公開カタログ経路を確認したところ、保存済み認証なし、対象ホストのカタログ404だった。device loginを案内しながら独立作業を進める。認証が成立しない場合はUnbrowse収集性能を主張しない。

既存のAtlas保存・根拠検証・Codex SDK仕様化を再利用する。18件の少数・逐次・読取GETで、通常応答、必須項目の欠落、日付・期間境界を確認する。課金契約・キー推測・認証回避・変更操作・大量探索は行わない。保護APIの成功応答はキーなしで検証できたと扱わない。

## 証拠と答え合わせの分離

- 分析入力: `data/weathernews-research/observations/` の実HTTPリクエスト・ステータス・ヘッダー・本文のみ。
- 正解側: 公開ドキュメントが配信しているJavaScriptアセット中のOpenAPIを、実行せずTypeScript ASTでリテラルとして読み取る。天気の共通定義と花粉の個別定義を別保管する。
- Codex SDKには正解側を渡さない。生成後に照合する。公開仕様と実挙動が不一致の場合は、モデルの誤りと仕様の不一致を別に記録する。

API仕様はLLMが解釈する。コードはJSON形式、引用一致、証拠参照、保存、公開スキーマの型・必須・pattern等の契約確認に限定する。Weathernews用の語句判定・固定応答を製品コードへ追加しない。

## 最小の実装変更

既存の取得経路はpublic-catalog/existing-resultsしか表せないため、直接観測をUnbrowseの成果と誤表示しない目的でdirect-httpの経路識別子と表示名を追加する。新しい収集エンジンは作らない。DBは既存の文字列列を利用しmigration不要。直接HTTPの証拠は既存のhttp-observed属性で保存する。

## 検証と完了条件

1. 部分: 直接HTTPという由来が保存・再読込後も保持される回帰試験。
2. 結合: 18観測→SQLite/証拠ファイル→実Codex SDK→引用検証→Snapshot/Markdown。
3. 通し: 公開仕様との照合表、実ブラウザの結果確認。

18応答の記録、観測だけからの仕様案、公開仕様との一致・差異・未検証の区別、閲覧・出力ができれば今回の分析は完了とする。Unbrowse未認証と保護APIの成功未検証は明示して残す。
